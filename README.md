# Polymarket — клон рынков предсказаний

Веб-приложение в структуре и стилистике polymarket.com, работающее на **реальных
публичных данных Polymarket**. Торговля бумажная: рынки, цены, стакан и история
котировок настоящие, а сделки виртуальные и хранятся локально в браузере.

Ценообразование считается **боевым движком биржи заказчика**, перенесённым на
фронт: нокаут-модель плеча, тариф за риск, риск-движок пула, LMSR робота, TWAP.
Исходники бэкенда лежат в [`backend/`](backend/README.md) — см. разделы ниже.

**Живая версия:** https://polymarket-rust-psi.vercel.app

Публикуется автоматически из ветки `main`: каждый push в
`github.com/dadernov/polymarket` собирает и выкатывает новую версию.

## Запуск локально

```bash
npm ci && npm run dev
```

Открыть http://localhost:3000

## Источники данных

Все четыре API публичные, без ключей и авторизации. Браузер к ним напрямую не
обращается — запросы идут через свои route handlers в `src/app/api/*`, что снимает
CORS, даёт единое место нормализации и серверный кэш.

| Источник | Что берём |
| --- | --- |
| `gamma-api.polymarket.com` | события, рынки, теги, поиск (`/events`, `/markets`, `/tags`, `/public-search`) |
| `clob.polymarket.com` | стакан заявок и история цен (`/book`, `/books`, `/prices-history`) |
| `data-api.polymarket.com` | лента сделок и держатели позиций (`/trades`, `/holders`) |
| `lb-api.polymarket.com` | рейтинги по обороту и прибыли (`/volume`, `/profit`) |

Gamma отдаёт часть полей JSON-строками (`outcomes`, `outcomePrices`,
`clobTokenIds`) — разбор и приведение к моделям `MarketEvent` / `Market` /
`Outcome` живёт в [`src/lib/polymarket.ts`](src/lib/polymarket.ts).

## Торговая математика

Вся торговая математика изолирована в `src/lib/pricing/` за двумя фасадами:
спот — `quote()`, плечо — `quoteLeverage()`. Больше нигде в проекте расчётов
нет, ни один компонент не считает цены сам.

Плечевой слой раньше считался по своей приближённой модели — она стояла
временно, до тех пор пока заказчик не пришлёт настоящую. Теперь за фасадами
**перенос боевого движка его биржи**: те же формулы, что считает бэкенд из
[`backend/`](backend/README.md). Перенос не построчный — берётся формула, а не
реализация; сверка с эталоном идёт по числам.

| Модуль | Что считает | Источник в `backend/` |
| --- | --- | --- |
| `ticks.ts` | цена 0..1 ⇄ целые тики 0..100, округление половины к чётному | тиковая модель всего бэкенда |
| `knockout.ts` | уровень нокаута, размер позиции, макс. убыток игрока и выплата пула | `services/leverage/knockout.py` |
| `tariff.ts` | цена за риск: капитал + гэп-премия + маржа платформы | `services/leverage/tariff.py` |
| `lambda-source.ts` | λ/J за интерфейсом-швом; сегодня статическая таблица калибровки | `services/leverage/lambda_source.py` |
| `calibration.ts` | оценка λ(d) и J(d) по ряду цен | `services/pipeline/calibrate.py` |
| `pool-risk.ts` | неттинг лонг/шорт и три лимита пула | `services/leverage/pool_risk.py` |
| `leverage.ts` | фасад для UI: котировка плечевой позиции, переоценка, P&L | — |
| `lmsr.ts` | ценовое ядро робота-маркетмейкера | `services/robot/lmsr.py` |
| `orderbook-engine.ts` | сведение заявки по реальному стакану CLOB | `matcher/internal/book` |
| `../oracle/twap.ts` | время-взвешенная средняя цена за окно | `services/oracle/twap.py` |

**Нокаут-модель.** Токен вероятности живёт в [0,1], поэтому максимальный убыток
конечен и известен заранее. Игрок вносит маржу, равную этому убытку: ликвидаций
и margin call нет, долг невозможен в принципе. Вместо ликвидации — нокаут-тик,
на котором маржа исчерпана и позиция гаснет. Плечо строго в (1, 5].

**Тариф — три слагаемых.** `стоимость капитала + гэп-премия + маржа платформы`.
Гэп-премия оплачивает то, что цена не обязана касаться нокаута плавно — она
может прыгнуть сквозь барьер, и перелёт платит пул. Размер прыжка описывают два
числа: λ(d) — доля шагов, пробивших барьер d, и J(d) — средний перелёт среди
пробивших; премия равна `λ·J·запас`. λ/J приходят через интерфейс
`LambdaJSource`, а не константами, поэтому подмена калибровки не трогает формулу
тарифа.

**Риск-движок пула.** Лонги и шорты по рынку неттятся, риском считается чистый
перекос. Три лимита — в терминах максимальной выплаты, а не номинала: ≤3%
капитала на рынок, ≤10% на кластер коррелированных рынков, ≤30% на весь пул.

**LMSR робота.** `C(q) = b·ln(e^(q_yes/b) + e^(q_no/b))`, цена покупки берётся
разностью `C(после) − C(до)`, а не «цена × объём», — каждый следующий билет
дороже предыдущего. Максимальный убыток маркетмейкера ограничен `b·ln 2`, цена
зажата в коридор [0.001, 0.999].

**TWAP-оракул.** Средняя цена за 30-минутное окно, взвешенная временем. Шип на
секунду почти не двигает среднее — на этом держится защита нокаутов и резолюции
от манипуляции ценой в один тик.

### Точка подмены

Она сработала ровно как задумано, и именно в неё встал реальный движок: весь
плечевой слой переписан под фасадом `leverage.ts`, ни один компонент не
правился. Спот по-прежнему считается проходом по стакану — это тот же алгоритм,
что в `matcher/internal/book`.

Строка `activeEngine` в [`src/lib/pricing/index.ts`](src/lib/pricing/index.ts)
остаётся входом для замены спотового движка: реализуйте `PricingEngine`,
замените одну строку. Требования к замене (чистота, отсутствие исключений и
NaN, режимы `amount`/`shares`, лимитные цены, комиссия) — в шапке того же файла.

## Бэкенд заказчика (`backend/`)

Исходники биржи, присланные заказчиком: Solidity-контракты под Foundry,
матчинг-движок на Go, Python-сервисы (робот, калибровка, плечевой слой, оракул).
Фронтенд их **не собирает и не импортирует** — они лежат ради версионирования,
чтения и следующего этапа. Разбор по файлам и команды запуска —
[`backend/README.md`](backend/README.md).

Деление ровно по одному признаку: нужен ли процесс на сервере.

- **Чистая математика — уже на фронте** (таблица выше). Считает предпросмотр:
  сколько это будет стоить и где сгорит позиция.
- **Всё остальное требует сервера и на Vercel не разворачивается:** матчер
  (постоянный процесс, gRPC на `:50051`, стакан в памяти), Redpanda как журнал
  сделок, контракты (нужна нода), Python-сервисы (робот держит соединение с
  матчером, пайплайн ходит во внешние API, TWAP нужен непрерывный поток
  наблюдений цены).

Это следующий этап; сейчас фронт с матчером и контрактами не связан и берёт
данные из публичного API Polymarket. От того, что формулы совпадают, предпросмотр
и будущее исполнение сойдутся.

Требования для запуска бэкенда: Docker (`infra/docker-compose.yml` поднимает
Redpanda), **Go 1.25+**, Foundry, Python с `pytest` и `numpy` (плюс `grpcio`,
`protobuf`, `requests` для робота и пайплайна).

## Как устроена бумажная торговля

- Стартовый баланс **$10 000**, состояние в `localStorage` (`pm.portfolio.v1`).
- Покупка: сумма в долларах проходит по реальному стакану выбранного исхода,
  движок возвращает среднюю цену, число акций, проскальзывание и комиссию.
- Продажа: задаётся числом акций из имеющейся позиции; реализованный
  результат считается относительно средней цены входа.
- Позиции переоцениваются по середине текущего стакана; если стакана нет —
  по цене входа.
- Комиссия по умолчанию `DEFAULT_FEE_BPS = 0` — меняется там же, в `pricing/`.
- Плечо (турбо) считается по нокаут-модели: маржа равна максимальному убытку,
  вместо ликвидации нокаут-тик, тариф за риск списывается вперёд. Цена входа
  округляется к целому тику, поэтому в котировке она может отличаться от той,
  что показана в стакане, на доли цента.

## Деплой на сервер

Нужен Node.js **20.9+** (Next.js 16 не работает на Node 18). База данных и
секреты не требуются. Каталог `backend/` в сборку не входит — Next.js его не
компилирует, Vercel игнорирует; для него нужен отдельный сервер (см. выше).

```bash
npm ci && npm run build && npm start
```

Слушает порт 3000 — меняется через `PORT` или `next start -p 8080`. Сверху
обычно ставят nginx или Caddy для TLS и systemd либо PM2, чтобы процесс
поднимался после перезагрузки.

Единственная переменная окружения, и она опциональная:

```bash
SITE_URL=https://ваш-домен.ru
```

Без неё сайт полностью работает, но `canonical` и ссылки OpenGraph/Twitter
указывают на `localhost` — то есть ломаются превью ссылок в мессенджерах и
поисковая индексация. На Vercel подставляется автоматически из `VERCEL_URL`.

Серверу необходим **исходящий HTTPS** к четырём хостам `*.polymarket.com`.
Проверить до деплоя:

```bash
curl -s -o /dev/null -w "%{http_code}\n" "https://gamma-api.polymarket.com/events?limit=1"
```

Ожидается `200`. Если `403` — Polymarket ограничивает адреса дата-центров, и
понадобится прокси для исходящих запросов; адреса собраны в четырёх константах
в начале [`src/lib/polymarket.ts`](src/lib/polymarket.ts).

## Ограничения

- Сделки виртуальные: ни кошелька, ни ончейн-транзакций, ни реальных денег.
- **λ/J откалиброваны на одном рынке.** Статическая таблица в
  `lambda-source.ts` получена заказчиком на 1001 точке цены одного
  Bitcoin-рынка Polymarket с шагом 10 минут — около семи суток истории. Этого
  достаточно, чтобы показать, что метод работает (λ убывает с ростом барьера, J
  растёт, на синтетике с известными параметрами оценка сходится к заложенному
  ответу), но **для боевого запуска нужен массовый прогон**: много рынков,
  разные классы событий и уровни ликвидности, разбивка по режимам рынка и
  регулярный пересчёт. До тех пор гэп-премия — оценка по одному активу. Шов под
  замену готов: тариф зависит от интерфейса `LambdaJSource`.
- Плечевой слой считается на фронте как предпросмотр. Пул, матчер и контракты не
  подключены — позиция никем не резервируется, лимиты пула проверяются только
  когда риск-движку явно передали состояние.
- Рынки не резолвятся — выплата по выигравшему исходу не начисляется
  автоматически, позиция просто остаётся в портфеле.
- Комментарии к событиям Gamma отдаёт отдельным API — счётчик показывается,
  сами комментарии не загружаются.

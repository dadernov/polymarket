# Бэкенд биржи предсказаний с плечом

Исходники бэкенда, присланные заказчиком. Здесь они лежат ради версионирования и
чтения — фронтенд их не собирает и не импортирует.

---

## Что это за система

Биржа предсказаний на бинарных рынках (ДА/НЕТ) с плечевым слоем поверх.

Базовая единица — пара токенов ДА+НЕТ, которая всегда стоит ровно $1. Пользователь
покупает ту сторону, в которую верит; цена токена и есть вероятность события в
глазах рынка. Поверх спота работает плечевой слой: игрок вносит маржу, пул выдаёт
позицию с плечом до 5x и уровнем **нокаута** — цены, при касании которой позиция
гаснет, а игрок теряет ровно маржу и не больше.

Цены везде живут в **целых тиках**: 1 тик = $0.01, диапазон 0..100. Деньги в
контрактах — микро-USDC (6 знаков). Float допускается только в аналитике
off-chain, никогда — в расчёте денег на цепочке.

### Принцип: сервисы считают и предлагают, контракт проверяет и исполняет

Ключевое архитектурное решение, проходящее через весь код.

Вся тяжёлая математика — сведение заявок, LMSR-котировки, неттинг лонгов и шортов,
тариф за риск, лимиты пула — считается **off-chain**, в Go и Python. Результат этих
расчётов — не приказ, а **предложение**.

Контракт принимает предложение и самостоятельно проверяет инварианты, которые
нельзя нарушать никогда:

* `ConditionalTokens` — коллатерал в контракте всегда равен числу выпущенных пар
  ДА+НЕТ. Токены нельзя напечатать из воздуха.
* `Settlement` — сводит две подписанные EIP-712 заявки атомарным свопом, проверяет
  подписи, сроки и учитывает уже исполненный объём по дайджесту заявки. Матчер
  может предложить сделку дважды — исполнится она один раз.
* `LeveragePool` — суммарный резерв под открытые позиции не может превысить
  `капитал * лимит утилизации`. Off-chain-риск-движок считает тот же лимит, но
  последнее слово за контрактом.

Смысл: ошибка или компрометация off-chain-части приводит к плохой цене или
отказу, но не к потере коллатерала.

## Из чего состоит

### `contracts/` — Solidity, сборка Foundry

| Файл | Что делает |
| --- | --- |
| `src/ConditionalTokens.sol` | Минимальный бинарный conditional token: `splitPosition` (коллатерал → пара ДА+НЕТ), `mergePositions` (обратно), `reportPayouts` оракулом, `redeemPositions` выигравшей стороны. Есть операторы в стиле ERC-1155 (`setApprovalForAll`, `transferPosition`) — их использует `Settlement`. |
| `src/Settlement.sol` | Атомарный своп по двум подписанным EIP-712 заявкам. Матчер сводит, контракт проверяет и исполняет. Защита от повторного исполнения через `filled[digest]`. |
| `src/LeveragePool.sol` | Пул плечевого слоя: капитал, резерв под позиции, жёсткий лимит утилизации в базисных пунктах. Резервирует и освобождает обязательства по id позиции. |
| `src/MockUSDC.sol` | Тестовый стейбл с 6 знаками и открытым `mint`. Только для testnet. |
| `src/LeveragePool.invariant.t.sol` | Инвариант-тесты пула (фаззинг). Лежит рядом с исходником, а не в `test/` — так было у заказчика. |
| `test/ConditionalTokens.t.sol`, `test/Settlement.t.sol` | Юнит-тесты токенов и сеттлмента. |

Компилятор — `solc 0.8.24`, оптимизатор включён (200 прогонов), фаззинг 256
прогонов, инварианты 256×32 (`foundry.toml`).

Единственная внешняя зависимость — `forge-std` v1.16.2 (`contracts/foundry.lock`).
Сам код библиотеки сюда не копировался, его ставит `forge install`.

Файл `.gitmodules` перенесён как есть, но как конфиг git здесь не работает: он лежит
в `backend/`, а путь внутри (`contracts/lib/forge-std`) отсчитывается от корня
репозитория. Он сохранён как запись о происхождении зависимости; фактическую версию
фиксирует `foundry.lock`.

### `matcher/` — матчинг-движок на Go

Центральный лимитный стакан с приоритетом «цена, затем время».

* `internal/book` — стакан одного рынка. Уровни цен с FIFO-очередями, индекс для
  отмены за O(1). Здесь же `Normalize` — приведение внешних терминов
  (ДА/НЕТ × купить/продать) к внутренним (bid/ask по ДА): «купить НЕТ по 40» это то
  же самое, что «продать ДА по 60». Стакан **намеренно не потокобезопасен**.
* `internal/engine` — владелец всех стаканов. Единственная горутина читает команды
  из канала и по очереди применяет их к книгам. Мьютексов нет by design: к стакану
  прикасается только владелец, конкурентность решается владением, а не блокировками.
* `internal/journal` — публикация сделок в durable-лог Redpanda (топик `fills`,
  клиент franz-go). Реплеябельный журнал — защита от ghost-fills: сделка сначала
  записана, потом видна.
* `proto/matcher.proto` + `gen/matcherv1` — gRPC-интерфейс: `Submit`, `Cancel` и
  серверный стрим `StreamFills`. Сгенерированный Go-код закоммичен, чтобы сборка не
  требовала `protoc`.
* `cmd/matcher` — сервер (gRPC на `:50051`), `cmd/democlient` — демо-клиент,
  подписывается на поток сделок и отправляет пару заявок.

### `services/` — Python

**`robot/` — робот-маркетмейкер на LMSR.**
`lmsr.py` — ценовое ядро: функция стоимости `C(q) = b·ln(e^(q_yes/b) + e^(q_no/b))`,
цена покупки берётся как разность `C(после) − C(до)`, а не `price × qty` — каждый
следующий билет чуть дороже предыдущего. Максимальный убыток маркетмейкера ограничен
`b·ln 2`. Цена зажата в коридор `[0.001, 0.999]`: на ровных 0 или 1 робот брал бы
риск бесплатно. `ladder.py` строит из одной справедливой цены лесенку бидов и асков
(3–5 уровней с каждой стороны). `robot.py` связывает это с матчером по gRPC: при
сделке двигает счётчики `q_yes`/`q_no` и перецентровывает лесенку. `taker.py` —
скрипт-«пользователь», бьёт по котировке робота.

**`pipeline/` — калибровка λ/J.**
Плечевая позиция гаснет на нокаут-барьере, но цена не обязана пройти барьер плавно —
она может прыгнуть сквозь него, и перелёт оплачивает пул. Пайплайн измеряет два
числа для каждого расстояния до нокаута `d`: **λ(d)** — доля шагов, пробивших барьер,
и **J(d)** — средний перелёт за барьер среди пробивших. Произведение `λ·J` и есть
ожидаемый убыток пула от прыжков на позицию. `synthetic.py` — генератор рядов
прыжок-диффузия (частота и размер прыжков заданы, значит правильный ответ калибровки
известен заранее — так проверяется сам метод). `fetch_polymarket.py` качает реальную
историю рынка через Gamma/CLOB API. `calibrate.py` — сама оценка,
`run_real.py` — прогон на живом ряде.

**`leverage/` — плечевой слой.**
`knockout.py` — по (направление, вход, плечо, маржа) считает уровень нокаута, размер
позиции, максимальный убыток игрока (по построению равен марже) и максимальную
выплату пула. `tariff.py` — цена за риск, три слагаемых:
`тариф = стоимость капитала + гэп-премия (λ·J·запас) + маржа платформы`.
`lambda_source.py` — шов под калибровку: тариф зависит от интерфейса `LambdaJSource`,
а не от того, откуда взялись числа. `pool_risk.py` — риск-движок: неттинг лонгов и
шортов по рынку и трёхуровневые лимиты в терминах максимальной выплаты, а не
номинала (≤3% капитала на рынок, ≤10% на кластер коррелированных рынков, ≤30% на
весь пул).

**`oracle/` — TWAP.**
Время-взвешенная средняя цена за окно (по умолчанию 30 минут). Цена держится на
уровне `p` от одного обновления до следующего, вклад отрезка в среднее — `p × Δt`.
Мгновенный шип почти не двигает среднее — на этом и держится защита нокаутов и
разрешения рынков от манипуляции ценой в один тик.

### `infra/`

`docker-compose.yml` — инфраструктура для локального/серверного прогона.

## Как это соотносится с фронтендом

Бэкенд делится на две части по одному признаку: нужен ли ему сервер.

**Чистая математика — уже на фронте.** Формулы, которым не нужны ни сеть, ни
процесс, ни нода, считаются прямо в браузере. Они перенесены в `src/lib/pricing/`:

| Здесь | На фронте |
| --- | --- |
| `services/robot/lmsr.py` — ценовое ядро LMSR | `src/lib/pricing/lmsr.ts` |
| `services/leverage/knockout.py` — нокаут, размер позиции, обязательство пула | `src/lib/pricing/knockout.ts` |
| `services/leverage/tariff.py` — тариф за риск | `src/lib/pricing/tariff.ts` |
| `services/leverage/lambda_source.py` — шов под калибровку λ/J | `src/lib/pricing/lambda-source.ts` |
| `services/leverage/pool_risk.py` — неттинг и лимиты пула | `src/lib/pricing/pool-risk.ts` |
| сведение заявок по стакану из `matcher/internal/book` | `src/lib/pricing/orderbook-engine.ts` |

Тиковая модель цены вынесена в `src/lib/pricing/ticks.ts` — это граница между долями
Polymarket (0.9995) и целыми тиками бэкенда. Округление там — половина к чётному, как
у `round()` в Python: иначе фронт разошёлся бы с эталоном на единицу тика. Котировку
UI берёт в одной точке — `quote()` из `src/lib/pricing/index.ts`.

Перенос не построчный: берётся формула, а не реализация. На фронте она считает
предпросмотр — «сколько это будет стоить и где сгорит позиция». Настоящие цифры
позже придут с сервера, и от того, что формула одна и та же, предпросмотр и
исполнение сойдутся.

**Всё остальное требует сервера и на Vercel не разворачивается:** матчер (постоянный
процесс с gRPC-портом и стаканом в памяти), Redpanda, контракты (нужна нода) и
Python-сервисы — робот держит соединение с матчером, пайплайн ходит во внешние API,
TWAP-оракулу нужен непрерывный поток наблюдений цены. Это следующий этап; сейчас
фронт с ними не связан.

## Запуск на сервере

Ниже — по факту из файлов репозитория.

### Инфраструктура

```bash
docker compose -f infra/docker-compose.yml up -d
```

Поднимается **Redpanda** (Kafka-совместимый брокер): `9092` — Kafka API, `9644` —
админ. Данные в именованном томе `redpandadata`, есть healthcheck через
`rpk cluster health`.

`postgres` (TimescaleDB), `redis` и `anvil` в compose-файле **закомментированы** —
заказчик оставил их на будущее, сейчас они не нужны.

### Матчер

Нужен **Go 1.25+** (`go.mod`: `go 1.25.0`). Зависимости — franz-go, grpc,
protobuf; сгенерированный proto-код уже в `gen/`, `protoc` не требуется.

```bash
cd matcher
go mod download
go test ./...              # тесты стакана и движка
go run ./cmd/matcher       # gRPC на :50051, журнал в Redpanda на localhost:9092, топик fills
go run ./cmd/democlient    # в другом терминале: подписка на поток сделок + пара заявок
```

Адреса зашиты в `cmd/matcher/main.go` константами — флагов и переменных окружения
нет, для другого окружения правится код.

### Контракты

Нужен Foundry. Библиотеки в репозиторий не копировались:

```bash
cd contracts
forge install          # подтянет forge-std v1.16.2 в lib/
forge build
forge test
```

`out/`, `cache/` и `lib/` — генерируемые, в git не попадают.

### Python-сервисы

Нужны **pytest** и **numpy**. Дополнительно: `grpcio` + `protobuf` для робота
(`robot.py`, `taker.py`), `requests` для `pipeline/fetch_polymarket.py`.

Модули импортируют друг друга по плоским именам (`from knockout import ...`),
поэтому **команды запускаются из каталога самого сервиса**, не из корня:

```bash
(cd services/leverage && pytest -q)   # 26 тестов
(cd services/oracle   && pytest -q)   #  7 тестов
(cd services/robot    && pytest -q)   # 12 тестов
(cd services/pipeline && pytest -q)   # 10 тестов
```

Все 55 тестов проходят — проверено.

Робот (требует поднятого матчера):

```bash
cd services/robot
python robot.py        # выставляет лесенку вокруг цены LMSR и держит её
python taker.py 100 55 # в другом терминале: купить 100 ДА по цене <= 55 тиков
```

Калибровка:

```bash
cd services/pipeline
python run_real.py                                   # прогон по polymarket_series.csv
python fetch_polymarket.py search bitcoin            # найти событие
python fetch_polymarket.py fetch <event-slug> [idx]  # скачать историю в CSV
```

## Известное ограничение

**Калибровка λ/J сделана на одном рынке.** `services/pipeline/polymarket_series.csv`
— это 1001 точка цены одного Bitcoin-рынка Polymarket с шагом 10 минут, около семи
суток истории. На нём получена таблица барьеров 1/2/3/5/10 тиков, и её значения
зашиты константами в `StaticLambdaJSource` (`services/leverage/lambda_source.py`),
откуда их берёт тариф.

Этого достаточно, чтобы показать, что **метод работает**: λ убывает с ростом барьера,
J растёт, премия ведёт себя осмысленно, а на синтетике с известными параметрами
оценка сходится к заложенному ответу.

Для боевого запуска нужен массовый прогон — много рынков, разные классы событий,
разная ликвидность, с разбивкой по режимам рынка и регулярным пересчётом. Заказчик
об этом знает; под замену уже сделан шов: `tariff.py` зависит от протокола
`LambdaJSource`, поэтому источник чисел меняется без правки формулы тарифа.

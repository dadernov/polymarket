# HANDOFF — «Кворум», рынки предсказаний

Документ для следующего агента с чистым контекстом. Проект живой и задеплоен,
ничего не сломано и не брошено на середине.

- **Код:** https://github.com/dadernov/polymarket (приватный, ветка `main`)
- **Живая версия:** https://polymarket-rust-psi.vercel.app
- **Локально:** `~/Desktop/projects/polymarket`
- **Объём:** фронт — 102 файла, ~17 000 строк; Next.js 16.2.12, React 19.2.4.
  Плюс `backend/` — исходники заказчика (~3 800 строк Go/Python/Solidity),
  фронт их не собирает и не импортирует.

---

## Goal / Цель

Собственный аналог Polymarket для западной аудитории на **реальных публичных
данных Polymarket**. Торговля бумажная: рынки, цены, стакан и история котировок
настоящие, сделки виртуальные и живут в `localStorage`.

Заказчик прошёл четыре содержательных этапа требований:

1. Полная реализация клона на трастовых источниках.
2. Плечевые позиции как главное отличие от Polymarket — модель «турбо/нокаут»
   с полным обеспечением, без ликвидаций и margin call.
3. **Отказ от копирования интерфейса Polymarket** в пользу собственного языка:
   «более приятный и понятный фронт, новое, красивое».
4. **Свой бэкенд.** Заказчик прислал готовую и покрытую тестами биржу —
   контракты, матчер, сервисы. Чистая математика (работает без сервера, едет на
   Vercel) перенесена на фронт; матчер, контракты и сервисы требуют сервера и
   ждут следующего этапа.

Отдельно и неоднократно: **математику ценообразования заказчик правит сам**,
поэтому она обязана оставаться изолированной. Требование окупилось ровно на
четвёртом этапе: его математика встала на место временной модели, не задев ни
одного компонента.

## Current Progress / Что сделано

### Экраны
Главная (герой «главный вопрос дня» + лента суточных движений + каталог),
каталог рынков с фильтрами, страница события (график, разбор исхода, список
рынков, панель сделки, стакан, вкладки Активность/Держатели/Правила/Обсуждение),
портфель-дашборд, лидерборд с подиумом, глобальная лента сделок. Тёмная и
светлая темы, мобильная вёрстка, поиск по ⌘K.

### Данные
Четыре публичных API Polymarket без ключей, через собственные route handlers
в `src/app/api/*` (обход CORS + единая нормализация + серверный кэш):
`gamma-api` (события, рынки, теги, поиск), `clob` (стакан, история цен),
`data-api` (сделки, держатели), `lb-api` (рейтинги).

### Торговля
Бумажный счёт $10 000. Спот через `quote()` по реальному стакану. Плечо —
турбо/нокаут: маржа равна максимальному убытку, вместо ликвидации нокаут-тик,
долг невозможен. Плечо строго в (1, 5]; **динамического потолка больше нет** —
прежнее снижение максимума у краёв диапазона и ближе к резолюции было нашей
выдумкой и не пережило сверку с кодом заказчика.

### Бэкенд заказчика в репозитории
Появился каталог `backend/` — присланные заказчиком исходники его биржи:
Solidity-контракты под Foundry (`ConditionalTokens`, `Settlement`,
`LeveragePool`), матчинг-движок на Go (центральный лимитный стакан, gRPC,
журнал сделок в Redpanda), Python-сервисы (робот-маркетмейкер на LMSR,
калибровка λ/J, плечевой слой, TWAP-оракул). Всё покрыто тестами, они проходят.
Фронт эти исходники **не собирает и не импортирует**, Vercel их игнорирует;
лежат ради версионирования, чтения и следующего этапа. Разбор по файлам с
командами запуска — `backend/README.md`.

Артефакты сборки закрыты в `.gitignore`: `contracts/lib|out|cache|broadcast`,
`__pycache__`, `.pytest_cache`, бинарники матчера.

### Математика — теперь боевая, не временная модель
Плечевой слой в `src/lib/pricing/` больше не своя приближённая модель, а перенос
движка заказчика; спот как считался проходом по реальному стакану, так и
считается. Перенос не построчный: берётся формула, а не реализация.

| Фронт | Источник |
| --- | --- |
| `ticks.ts` | тиковая модель: цена 0..1 ⇄ целые тики 0..100 |
| `knockout.ts` | `services/leverage/knockout.py` |
| `tariff.ts` | `services/leverage/tariff.py` |
| `lambda-source.ts` | `services/leverage/lambda_source.py` |
| `calibration.ts` | `services/pipeline/calibrate.py` |
| `pool-risk.ts` | `services/leverage/pool_risk.py` |
| `lmsr.ts` | `services/robot/lmsr.py` |
| `orderbook-engine.ts` | сведение по стакану из `matcher/internal/book` |
| `src/lib/oracle/twap.ts` | `services/oracle/twap.py` |

Что это даёт по существу: нокаут-модель (маржа = максимальный убыток, вместо
ликвидации нокаут-тик); тариф из трёх слагаемых — стоимость капитала +
гэп-премия `λ·J·запас` + маржа платформы, где λ/J приходят через интерфейс
`LambdaJSource`, а не константами; риск-движок пула с неттингом лонг/шорт и
тремя лимитами в терминах максимальной выплаты (3% на рынок, 10% на кластер,
30% на пул); LMSR робота с ценой как разностью функций стоимости и потолком
убытка `b·ln 2`; TWAP за 30-минутное окно.

Границу «доли Polymarket → целые тики бэкенда» держит `ticks.ts` — единственное
место, где цена меняет шкалу. UI ходит в математику через два фасада: `quote()`
для спота и `quoteLeverage()` для плеча.

### Дизайн-система «Ledger»
`src/app/globals.css` — тёплые нейтрали вместо сине-серого металла (тот
читается как «ещё один крипто-интерфейс»), индиго вместо дефолтного синего,
изумруд и роза вместо светофорных цветов, антиква Playfair Display для крупных
чисел и заголовков, светлая тема основная. **Имена токенов не менять** — на них
завязаны все компоненты, смена значений меняет вид всего приложения разом.

## What Worked / Что сработало

**`negRisk` как признак взаимоисключительности.** Проверено на выборке из 25
событий, расхождений ноль: `true` — рынки отвечают на один вопрос и сумма цен
≈ 1; `false` — набор независимых ставок (у матча их до 32, сумма доходит до 13).
Поле пробрасывается в модель как `exclusive` и определяет всю подачу карточки.
Без этого признака интерфейс сортировал пропы матча по цене и показывал три
строки по 100% — именно на это жаловался заказчик.

**Сохранение имён токенов при смене палитры.** Позволило переписать визуальный
язык целиком, не трогая сотни компонентов.

**Прогрев серверного кэша вместо предзагрузки маршрута** (см. ниже) — дал
2000 мс → 1 мс на переключении категории.

**Изоляция математики — окупилась полностью.** `src/lib/pricing/` за фасадами,
контракт описан в шапке `index.ts`, ни один UI-компонент не считает цены сам.
Когда пришёл настоящий движок заказчика, весь плечевой слой переписали под
фасадом `leverage.ts`, не тронув ни одного компонента: типы `LeverageQuote` и
`Quote` остались прежними, изменилось только то, что стоит за ними. Ради этого
изоляция и делалась.

**Формула, а не построчный перенос.** Питоновский код заказчика не
транслировался в TypeScript механически: бралась формула и переписывалась в
здешних терминах. Результат читается как обычный TS, а сверка с эталоном идёт по
числам, а не по строкам.

**Проверка на прод-сборке.** Предзагрузка Next.js работает **только в
продакшене**, поэтому мерить производительность в dev бессмысленно.

## What Didn't Work / Что не сработало

Не повторяйте — проверено эмпирически.

### Перенос математики

**`Math.round` вместо округления половины к чётному.** У Python `round()`
банковское округление, у JS — всегда вверх. Эталон заказчика для входа 73 тика
при плече 2 даёт нокаут **36**, а не 37, ровно потому, что 36.5 идёт вниз. С
`Math.round` фронт разъезжается с бэкендом на тик — а тик здесь это и цена, и
барьер для λ/J. Округление живёт в одном месте, `ticks.ts:roundHalfEven`.

**Динамический потолок плеча.** Прежняя здешняя модель снижала максимум у краёв
диапазона цены и ближе к резолюции. У заказчика такого нет: `MAX_LEVERAGE = 5`
статичен, а вход просто обязан быть строго внутри 0 < entry < 100 тиков.
Придуманное «улучшение» пришлось снять — авторитетна их модель.

**Наивный `exp()` в LMSR переполняется.** На больших счётчиках `e^(q/b)` уходит
в `Infinity`, и функция стоимости возвращает `NaN`. Нужен log-sum-exp с выносом
максимума за логарифм. Отдельно: цену нельзя пускать в ровные 0 и 1 — на них
робот берёт риск бесплатно, поэтому коридор [0.001, 0.999].

**Калибровать λ/J на произвольном шаге ряда нельзя.** λ — доля шагов, пробивших
барьер, поэтому она прямо зависит от того, как часто взяты точки: на часовых
шагах цена успевает уйти дальше, чем на десятиминутных, и λ выходит завышенной.
Эталонный ряд заказчика снят с шагом ~600 секунд, поэтому и калибровать надо на
сопоставимом шаге, иначе числа несравнимы с его таблицей. Плюс порог по объёму
выборки: мало точек — честнее откатиться на статическую таблицу, чем подставить
шум вместо статистики.

**`pytest` из корня `backend/` не работает.** Python-сервисы импортируют друг
друга по плоским именам (`from knockout import ...`), поэтому команды
запускаются из каталога самого сервиса: `(cd services/leverage && pytest -q)`.

**`.gitmodules` внутри `backend/` не действует.** Файл перенесён как есть, но
путь внутри (`contracts/lib/forge-std`) отсчитывается от корня репозитория, а
лежит он в подкаталоге. Это запись о происхождении зависимости, не рабочий
конфиг; фактическую версию фиксирует `contracts/foundry.lock`, ставит
`forge install`.

### Фронтенд

**`router.prefetch` не лечит задержку смены категории.** У динамической
страницы с `loading.tsx` предзагрузка забирает только оболочку. Замер: холодный
рендер категории ~1.0 с, из них ~0.9 с — ответ Gamma; повторный ~0.03 с. Узкое
место — апстрим, а не отрисовка. Помог прогрев по наведению через
`/api/events` с теми же параметрами: он делит с рендером страницы одну запись
кэша `fetch`. Плюс `staleTimes.dynamic` в `next.config.ts` (по умолчанию
динамические страницы на клиенте не кэшируются вовсе).

**Перенос стакана из прилипшей панели не решал недостижимость кнопки.** Панель
сделки одна занимает 917 px при доступных ~724 — внутренняя прокрутка нужна в
любом случае.

**Абсолютное центрирование навигации в шапке.** Правый блок наезжал на пункт
«Лидеры». Три колонки в потоке решили это. Но затем разворачивание подписей на
`xl` создало ту же проблему ровно на 1280 px (нужен 431 px при колонке 414) —
подписи перенесены на `2xl`. При правках шапки проверяйте 1024 / 1100 / 1280 / 1440.

**Headless Chrome со `--virtual-time-budget` зависает** и не завершается —
снимал экраны через панель браузера.

**`WebFetch` на ссылки claude.ai/share возвращает пустоту** — страницы
рендерятся на клиенте, нужен реальный браузер.

**Замеры геометрии при скрытой панели браузера дают нули** (`innerWidth: 0`) —
сначала снимок экрана, потом замер.

**`vercel --prod` из родительской папки.** Публикуйте только из каталога
проекта; лучше вообще не вручную — репозиторий подключён к Vercel, каждый
`git push` в `main` публикует сам.

**`setState` внутри `useEffect`** валит линтер (`react-hooks/set-state-in-effect`).
Сброс оптимистичного состояния делается во время рендера сравнением с
предыдущим значением параметра — образец в `src/components/market/sort-select.tsx`.

## Ограничения, которые легко принять за баги

- У спортивных событий многие пропы уже сыграны и честно показывают `<1%` и
  `>99%` — это реальные данные.
- В подиуме лидеров встречаются имена вида `||||||||||||` — так в API Polymarket.
- Спарклайн героя красится по недельному тренду, а дельта рядом суточная,
  поэтому они иногда расходятся в цвете. Формально верно, визуально спорно.
- Рынки не резолвятся: выплата по выигравшему исходу не начисляется
  автоматически, позиция остаётся в портфеле.
- В плечевой котировке цена входа округлена к целому тику: 0.734 показывается
  как 0.73. Это не потеря точности, а тиковая модель бэкенда — у него цены
  целые, и фронт обязан считать в той же шкале.
- Плечевая позиция считается как предпросмотр: пул её не резервирует, лимиты
  проверяются только если риск-движку явно передали состояние. Матчер и
  контракты не подключены.
- Несуществующее событие отдаёт корректную страницу «не найдено», но со
  статусом 200 — документированное поведение Next.js для потоковых ответов.

## Главное ограничение математики

**λ/J откалиброваны на одном рынке.** Таблица барьеров 1/2/3/5/10 тиков в
`lambda-source.ts` — результат прогона заказчика по
`services/pipeline/polymarket_series.csv`: 1001 точка цены одного Bitcoin-рынка
Polymarket с шагом 10 минут, около семи суток истории.

Этого хватает, чтобы показать, что **метод работает**: λ убывает с ростом
барьера, J растёт, премия ведёт себя осмысленно, а на синтетике с заранее
известными параметрами прыжок-диффузии оценка сходится к заложенному ответу.
Этого **не хватает для боевого запуска**: гэп-премия сегодня — оценка риска по
одному активу в одном режиме рынка.

Нужен массовый прогон: много рынков, разные классы событий, разная ликвидность,
с разбивкой по режимам и регулярным пересчётом. Заказчик об этом знает. Шов под
замену уже готов с обеих сторон — и в Python (`tariff.py` зависит от протокола
`LambdaJSource`), и на фронте (`tariff.ts` принимает `LambdaJSource`, реализация
подставляется снаружи). Формула тарифа при смене источника чисел не меняется.

## Next Steps / Следующие шаги

Математика закрыта — она больше не заглушка. Следующий этап один и он крупный:
**поднять серверную часть бэкенда и связать с ней фронт**. По убыванию ценности:

1. **Развернуть бэкенд на сервере.** Всё, что требует процесса, лежит в
   `backend/` и на Vercel не живёт. По порядку:
   - инфраструктура: `docker compose -f infra/docker-compose.yml up -d` —
     поднимается Redpanda (Kafka API `9092`, админ `9644`), данные в томе
     `redpandadata`. Postgres/TimescaleDB, redis и anvil в compose закомментированы
     заказчиком — пока не нужны;
   - матчер: **Go 1.25+**, `go mod download && go test ./... && go run ./cmd/matcher`
     (gRPC на `:50051`, журнал сделок в топик `fills`). Адреса зашиты
     константами в `cmd/matcher/main.go` — ни флагов, ни переменных окружения,
     для другого окружения правится код. Это первое, что придётся сделать
     при выносе на реальный хост;
   - контракты: Foundry, `forge install && forge build && forge test`.
     Библиотеки в репозиторий не копировались;
   - Python-сервисы: `pytest` и `numpy`, плюс `grpcio`/`protobuf` для робота и
     `requests` для пайплайна. Тесты запускаются **из каталога сервиса**, не из
     корня (плоские импорты).
2. **Связать фронт с матчером вместо публичного API Polymarket.** Сейчас стакан,
   история цен и лента сделок приходят с `clob`/`gamma`/`data-api`; после
   разворота матчера их место занимает свой стакан и свой поток сделок
   (`StreamFills` по gRPC — фронту понадобится шлюз, браузер в gRPC не ходит).
   Точка входа готова: весь фронт берёт данные через route handlers в
   `src/app/api/*` и модели `MarketEvent`/`Market`/`Outcome`, менять придётся
   слой источника, а не компоненты. Котировка уже считается теми же формулами,
   что у бэкенда, поэтому предпросмотр и исполнение сойдутся.
3. **Массовая калибровка λ/J** — см. раздел выше. Без неё гэп-премия остаётся
   оценкой по одному Bitcoin-рынку; для боевого запуска этого мало.
4. **Перенос фронта на свой сервер.** Друг заказчика разворачивает отдельно: `git clone`,
   далее `git pull && npm ci && npm run build` и перезапуск. Требуется Node.js
   **20.9+** (в Ubuntu из коробки 18 — не соберётся), около **1 ГБ RAM** на
   сборку и исходящий HTTPS к `*.polymarket.com`. Проверка до деплоя:
   `curl -s -o /dev/null -w "%{http_code}\n" "https://gamma-api.polymarket.com/events?limit=1"` — ожидается `200`.
5. **Свой домен.** Меняется одна переменная `SITE_URL` (Vercel → Settings →
   Environment Variables). Без неё `canonical` и OG-превью указывают на localhost.
6. **Общие аккаунты и портфели.** Сейчас бумажный счёт в `localStorage`, то есть
   у каждого посетителя свой. Для единого портфеля между устройствами нужны
   Postgres и авторизация — это отдельная работа, в проекте её нет.
7. **Фильтр решённых рынков в ленте**, если пропы с `<1%`/`>99%` мешают.

Должно быть чисто; допустимы ровно два предупреждения `no-img-element` — внешние

потому что приходят с разных CDN.

Дальше — прод-сервер и браузер: `npx next start -p 3121`. Проверять обе темы и
ширины 375 / 1024 / 1280 / 1440. Сквозной сценарий, который ловит регрессии
лучше всего: на странице события нажать «No» в строке другого рынка — панель
сделки, стакан, график и подсветка строки обязаны переключиться синхронно, а
введённая сумма сброситься. Этот рассинхрон был реальным багом, из-за которого
